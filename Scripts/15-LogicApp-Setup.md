
# 01 - Logic App Setup

## 1. Create Azure Logic App (Consumption)

Created an Azure Logic App through the Azure Portal.

### Configuration

| Setting | Value |
|---|---|
| Name | `logicapp-lab2-dev-09` |
| Region | Central US |
| Plan Type | Consumption |
| Log Analytics | No |
| State | Stateful |

### Configuration Details

- **Region (Central US):** Deploys the Logic App in the same region as the main project resources.
- **Plan Type (Consumption):** Uses a consumption-based pricing model, with costs primarily based on workflow trigger and action executions.
- **Log Analytics (No):** The Logic App was created without connecting it to a Log Analytics Workspace.
- **State (Stateful):** Maintains workflow execution state and retains run history for monitoring and troubleshooting.

### Purpose

The Logic App serves as the workflow automation component of Azure-Lab-02. It is designed to receive events from Azure Event Grid and execute configured workflow actions automatically.

### Creation Method

Created directly through the Azure Portal:

`Create a resource > Integration > Logic App (Consumption)`

## 2. Configure Event Grid Trigger

1. Open the Logic App named `logicapp-lab2-dev-09`.
2. Navigate to **Logic app designer** from the left-hand menu.
3. Select **Add a trigger**.
4. Search for `Event Grid` in the connector search field.
5. Select the **When a resource event occurs** trigger.

### Purpose

This trigger allows the Logic App to start automatically when a matching Azure resource event is received through Event Grid.

It acts as the entry point of the workflow, eliminating the need for manual execution or continuous polling.

### Trigger Configuration

Configure the following fields:

| Field | Value |
|---|---|
| Resource Type | `Microsoft.EventGrid/topics` |
| Subscription | `<YOUR_SUBSCRIPTION_ID>` |
| Resource Name | `evgt-azlab02-dev-centralus` |
| Event Type | `OrderCompleted` |

### Authentication

- **Authentication Method:** OAuth

OAuth was selected as the authentication method for connecting the Logic App to Azure resources.

### Purpose

These settings configure the Event Grid trigger to listen for `OrderCompleted` events generated by the `evgt-azlab02-dev-centralus` Event Grid Topic.

When a matching event is received, the Logic App automatically starts its workflow.

### Additional Trigger Settings

Leave the following fields empty:

- **Subject Begins With:** Empty
- **Subject Ends With:** Empty
- **Subscription Name:** Empty (if optional)

### Advanced Parameters

1. Keep all Advanced Parameters at their default values.
2. Do not modify the Trigger Settings.
3. Select **Publish** to save and publish the workflow configuration.

### Result

The Logic App workflow is published with the configured Event Grid trigger and is ready to receive matching `OrderCompleted` events.

These expressions extract the corresponding order properties from the `data` object of the incoming Event Grid event.

# 09 - Outbox Publisher Failure and Retry Testing

## 1. Implement Controlled Failure Injection

To test the Outbox Publisher failure handling and retry mechanism, the `OutboxPublisher.cs` file was modified to support controlled failure injection.

### Modify OutboxPublisher

Navigate to the following file:

`H:\Azure\Projects\Azure-Lab-02\OrderProcessor\OutboxPublisher.cs`

Replace the existing file content with the updated implementation containing:

- Controlled failure injection using `EnableFailureTest`.
- Targeted failure simulation using `FailureTestEventId`.
- First-attempt detection using the `Attempts` property.
- Diagnostic logging to Application Insights.
- Error logging through Application Insights.
- Failure recording through `dbo.usp_RecordOutboxEventFailure`.
- Successful publishing through Azure Event Grid.
- Publishing status updates through `dbo.usp_MarkOutboxEventPublished`.

### Purpose

The controlled failure injection mechanism allows a publishing failure to be simulated for a specific Outbox event.

The failure is injected only when:

- Failure testing is enabled.
- The configured Event ID matches the current Outbox event.
- The event is being processed for the first time (`Attempts = 0`).

This allows the retry behavior to be tested without depending on an actual Event Grid outage.

---

## 2. Verify Stored Procedure Output

Before building the project, verify that the `dbo.usp_GetPendingOutboxEvents` Stored Procedure returns the `Attempts` column.

The updated C# implementation reads this value to determine whether an event is being processed for the first time.

### SQL Query

Execute the following command in SQL Database Query Editor:

```sql

```

### Verification

Inspect the Stored Procedure definition and check whether `Attempts` is included in its SELECT statement.

The updated C# implementation requires this column.

---

## 3. Update the Stored Procedure

The existing Stored Procedure did not include the `Attempts` column in its output.

To resolve this, update it using the following SQL definition:

```sql
CREATE OR ALTER PROCEDURE dbo.usp_GetPendingOutboxEvents
AS
BEGIN
    SET NOCOUNT ON;

    SELECT TOP (10)
        EventId,
        EventType,
        Subject,
        DataVersion,
        EventData,
        Attempts
    FROM dbo.OutboxEvents
    WHERE PublishedAt IS NULL
    ORDER BY CreatedAt ASC;
END;
```

### Purpose

The `Attempts` column allows the Outbox Publisher to identify whether an event is being processed for the first time.

The application uses this value to ensure that the controlled failure is injected only once for the configured Event ID.

## 5. Test Objective

The purpose of this configuration is to validate the following Outbox Publisher behaviors:

- Simulate a controlled Event Grid publishing failure.
- Record the failure details in the Outbox database.
- Increment the event's `Attempts` counter.
- Keep the event pending while publishing has not succeeded.
- Allow the next Timer Trigger execution to retry publishing.
- Mark the event as published after a successful retry.

This provides a way to test failure handling and retry behavior in the Azure-Lab-02 event-driven architecture.
